# Peer Test

Resolve bundled files relative to this skill (its installed base directory), and application data relative to the explicit/active application workspace. Workspace settings: `.agents/skills/peer-review/settings.local.json`; optional nonsecret guidance: `hints.local.md`; ticket ledger/evidence: `.history/<ticket>/`. This workspace path is a data convention shared by every host, not a skill install location. Read the application's project guidance (AGENTS.md and/or CLAUDE.md, including files they import; read a shared file once) and hints once. Never create a separate peer-test AGENTS.md or CLAUDE.md. User instructions override this workflow. No commits, pushes, Jira comments/attachments or other external records without explicit authorization.

## Host agent

The workflow runs in Codex or Claude Code; only tool names differ.

- Invocation: Codex `$peer-test`; Claude Code `/peer-test <ticket>` or a request naming the skill. Treat trailing text as the ticket key plus overrides.
- Shell: run credential-free PowerShell helpers as `pwsh -NoProfile -File <skill>/scripts/<name>.ps1 ...` so they work from Bash or PowerShell tools; quote Windows paths. `-File` passes only strings, so never use it for a live `Invoke-PeerTest.ps1` run needing `-Credential` or `-ApiKey`: in one PowerShell session (the host's PowerShell tool, or a single `pwsh -NoProfile -Command` script), read the selected account from settings, build the PSCredential/SecureString in memory and call the runner there. Secrets never appear in arguments, command text or output; without them the runner prompts interactively, which an agent shell cannot answer. Run builds, long waits and services that do not detach in the background (Claude Code `run_in_background`) instead of blocking a foreground call past its timeout.
- Browser: use the host's browser tools. Codex: the background built-in browser. Claude Code: an isolated browser first (the desktop app's built-in browser pane, or a configured Playwright/browser MCP with its own profile), and Claude in Chrome only when neither exists or settings say `"chrome"`. Settings `browser: "iab"` means the host's built-in browser on either host; `"chrome"` means the user's Chrome (Claude in Chrome). Claude in Chrome shares the user's cookies across tabs: before logging in with a test account, check whether the target origin already has a session; if it does, ask the user before signing in or out there, since that changes their own session in every tab. Never sign out of or disturb the user's own sessions without that approval. With no browser tools, report UI cases BLOCKED rather than substituting API evidence.
- Jira: use the connected Atlassian MCP tools (Claude Code names them `mcp__<server>__*`; load deferred tools first). For expired OAuth, Codex renews with `codex mcp login atlassian`; Claude Code cannot start OAuth itself, so ask the user to reauthenticate through `/mcp`, then verify one Jira read.
- Progress: the ticket checklist is authoritative; a host task/plan list may mirror the current phase but never replaces it.

## Efficient routing

- Reuse the ticket checklist on resume; recover unfinished mutations, then continue the first runnable unchecked case. Do not repeat completed discovery/tests unless source, runtime or evidence changed.
- Prefer exposed Atlassian MCP tools. Fetch site identity once and the issue with decision-relevant/custom Peer Testing fields; save raw evidence locally, return only title/instructions/PR references. For invalid OAuth, diagnose once and reauthenticate the existing server (see Host agent). Do not propose another integration merely because tools are absent. Browser fallback is allowed when no usable API connection exists; explain it first. Do not repeat environment-wide diagnostics on healthy runs.
- For native MAUI iOS, read [ios-simulator.md](references/ios-simulator.md). Read [ios-setup.md](references/ios-setup.md) only for missing/broken infrastructure. Use `scripts/maui_peer.py` for compact preflight, cached source snapshots, bound sessions, observations and action batches. Select app-specific profiles; never copy another app's account/backend/event/selector assumptions.
- For browser checks, use the host browser tools above and supported computer-use APIs. For API plans, see [README.md](README.md); use `scripts/Invoke-PeerTest.ps1`. Live runner calls remain loopback HTTPS. Fixtures/recovery or unusual cases: load only the relevant section of [workflow-details.md](references/workflow-details.md), not the whole reference.
- Save full issue/PR data, XML, build logs and responses locally; return concise summaries and file links. Inspect focused callers/diffs, not whole repositories. Observe UI after a meaningful action batch; save screenshots at required distinct states and failures, not every tap. Check system alerts before repeating an unchanged native action.
- Reuse healthy services and verified setup profiles. Reuse a build only when current source/config/toolchain fingerprints AND the actually installed artifact match saved provenance; commit ID or an old manifest alone is insufficient. Otherwise refresh/build using authorized project instructions. New source snapshots are not proof of installed runtime parity.

## Timing and preflight

Capture startedUtc before the first ticket action, persist it immediately in the checklist, and preserve it across resumptions. After tests, investigation, restoration, evidence/report preparation and final verification, capture completedUtc and totalRunSeconds. Total wall-clock time includes setup, user waits, repairs and reporting. Put Total run time at the top of the final chat summary, report and Jira draft; use readable duration and the user's timezone. Keep runner time separate. If timing is missing, label it unavailable and explain any known partial interval; never infer a completion time or invent token savings.

1. Resolve workspace; run `scripts/Initialize-Settings.ps1 -WorkspacePath <workspace>`. Missing, invalid or unconfigured settings require the user to complete the exact local file and set configured=true. Do not overwrite/migrate settings, run tests, start services, log in or mutate fixtures/accounts while pending. Configured is not full readiness: validate selected environment, authorized origins, role and scope. No credentials in output, tool-call text, plans, scripts or evidence; load into memory, use PSCredential/SecureString where appropriate. Keep settings, hints and history Git-ignored. Never reuse another workspace's accounts or old shared configs.
2. Validate ticket key (letters-hyphen-digits); read actual issue/Peer Testing instructions and relevant PR. Inspect changed code, comments and callers. Record source revision and runtime parity. Derive distinct required scenarios and justified additional cases; never replace unread instructions with a generic plan. Clarify conflicting expectations before declaring a defect.
3. Check only dependencies needed for those cases: endpoint/service health, runtime, account role/session, sample records, feature access and limits. Start only missing required services using verified application guidance; never restart healthy or duplicate failing/listening services. Diagnose failures once before retrying. Read-only smoke precedes config/account/fixture changes. Providing credentials does not make an account disposable; missing delivery credentials may still permit queue-only coverage.
4. Snapshot recovery values/IDs, absence versus defaults, dates/counters and worker states; establish notification isolation before generating messages. Derive desired final account state from project guidance (it may differ from the starting state). Group foreseeable missing inputs/approvals once. Order scenarios by dependency, service, role and configuration; positive controls precede rejection/absence cases. Put final verification last.
5. Create/update the single durable checklist from `templates/checklist.md`. Before execution/mutation, publish consolidated preflight using `templates/preflight.md`: Ready/Needs input/Blocked, environment/role/scope, ticket/source/runtime, services/startup, account/feature readiness, recovery/isolation, required/additional/total counts, additions with reasons, execution groups, blockers and next step. Unknown stays unverified. Partial preflight is visible when blocked; tool logs do not replace it.

With 0–5 additional scenarios, proceed automatically within authorization. Above five, save the full ordered checklist and ask for all tests, required only or a selected subset (with recommendation); wait before dependent execution. More than five discovered later triggers the same question unless already approved. Count scenarios, not setup/assertions/repeated controls. Mark omitted cases NOT TESTED with reason. Do not ask again for unchanged scope or treat elapsed time as consent.

## Execute and recover

Use browser/native UI for visible behavior and APIs for data contracts/persistence, without duplicating assertions at every layer. Assert independently known values/records, not just success or empty results. After saves verify completion and persistence. Before asserting no side effect, establish a positive control. Batch by configuration state and record request counts separately from elapsed/token usage (only if known).

Update the checklist immediately after each scenario/batch and before interruption. Record IN PROGRESS plus recovery notes before mutations. `[x]` means terminal PASS, FAIL or deliberate NOT TESTED; BLOCKED stays unchecked with dependency/next action. Preserve ordered IDs, expected/actual, configuration and evidence. Runner results cover only API assertions; put batches in subdirectories so they cannot overwrite the ticket report. Replay proves saved-response/harness behavior, not current app behavior.

For temporary DB fixtures, use the guarded helper compatible with the app's verified data model; pass workspace SettingsPath for mutation and recovery, check destination/table/field mappings with ValidateOnly first. Other stores need a scoped transaction/baseline comparison/finally restoration/independent verification harness. No browser/native writes while a DB fixture is active. Fixtures are setup, not proof of UI editing/provisioning. Preserve recovery backups on termination/conflict; never overwrite concurrent changes.

Investigate failed assertions against code/response/UI and rerun affected cases only. Separate environment failure from product failure. Append bug candidates at the checklist end with stable ID, candidate/confirmed/disproved status, expected/actual, minimal repro, revision/evidence and investigation/retest; update the original entry rather than duplicating. Check intended behavior before confirming. Do not spawn agents or subagents by default. Give meaningful progress at least once a minute.

## Finish

Complete every authorized runnable required case and resolve stale PARTIAL/BLOCKED entries. Retain valid reusable records and normal audits; repair/remove dirty data interfering with later runs. Remove temporary credentials and potentially deliverable test messages; restore security/workers/transient counters/overrides and apply the application's desired final account state, including limits/subscription when relevant. Verify messages are clear before delivery restarts. Record retained data and independently verify final state.

Use `templates/report.md` and `templates/summary.md`. Report required/additional PASS/FAIL/BLOCKED/NOT TESTED separately; count failed cases separately from unique bugs. Include source/runtime, environment, meaningful evidence, scope/coverage limits and timing. Bugs Found contains confirmed findings or None found; unresolved observations/conflicts are separate. Never hide failures behind PASS. Use **✅ PASS** and **❌ FAIL** in displayed grids, retaining status words and unchanged machine statuses. Keep full matrices/provenance and restoration details in the report; chat omits restoration except blockers requiring user action. Final chat: ticket/title, bold result and Total run time, compact coverage table, stable bug IDs/pre-existing attribution when verified, limitations, report/checklist/draft links, and required proof screenshots after summary. State whether the Jira draft was posted.
