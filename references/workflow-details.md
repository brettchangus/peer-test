## Run timing

Capture startedUtc at the first action for a new ticket, before preflight; persist it in the checklist and preserve it across resumptions. Immediately before the final chat response, after testing, investigation, restoration, final-state verification and report/evidence preparation, capture completedUtc and calculate totalRunSeconds = completedUtc - startedUtc. Save timestamps and duration in the checklist/report. Total wall-clock run time includes setup, approvals/user waits, recovery and reporting. Runner time is separate; do not reset the whole-run timer when starting a fixture or runner. Separately measured waits may be reported without silently subtracting them.

Put Total run time in the opening summary of the final chat response, report and Jira draft. Use readable durations such as 28m 14s, and the user's timezone for displayed timestamps. Never label runner-only or testing-only time as total time. If timing was not captured, show Total run time: unavailable, then identify any known partial interval and its limits. Do not infer a missing completion time.

## Preflight

1. Resolve the target application workspace and run scripts/Initialize-Settings.ps1 -WorkspacePath <workspace>. If settings.local.json is missing, the helper copies the credential-free examples/settings.example.json to <workspace>/.agents/skills/peer-review/settings.local.json without overwriting an existing file. On NeedsConfiguration, show the exact path and ask the user to configure it before proceeding; do not run tests, start services, log in or change fixtures/account settings while pending. Do not silently migrate another workspace's settings or use old shared .config files. Existing invalid or unconfigured settings also require correction; never overwrite them. The user must fill the required environment/account settings and set configured to true. A Configured result only acknowledges setup; validate required values, selected environment/role, authorized origins and test scope independently before testing. Keep settings, local hints and run data Git-ignored (the helper creates local ignore rules); never echo credentials. Read the actual Jira issue and Peer Testing field using the connector, or the signed-in browser if unavailable. Validate ticket keys as letters followed by a hyphen and digits; the workspace selects settings, not the ticket prefix. Resolve application-specific guidance from the workspace's AGENTS.md/CLAUDE.md, conversation and optional .agents/skills/peer-review/hints.local.md; verify against current code/UI. Never substitute a generic checklist for unread instructions.
2. Follow the relevant PR and inspect changed code, method comments and callers. Record source revision and whether runtime matches. Reconcile conflicting expectations with user clarification before declaring a defect. Identify missing tests justified by changed behavior, boundary cases and likely regressions. Count distinct scenarios, not assertions or setup steps; mark each additional test with its reason.
3. Check only required dependencies: web/API/worker endpoints, account role/session, sample records, required account state and feature access, runtime freshness and runner compatibility. If a required service is not running, start it using verified instructions from the target application's AGENTS.md/CLAUDE.md and workspace's .agents/skills/peer-review/hints.local.md, then verify the endpoint responds. Use startup and build tools supported by the selected application; verify hosting and runtime requirements from its guidance. Do not restart healthy services or start unrelated workers. A responding but failing service needs diagnosis, not another process. Run a read-only smoke check before changing keys, permissions or test settings.
4. Group foreseeable missing inputs/approvals into one request. Existing authorization persists. Read credentials into memory; never print them, put them in tool-call text or save them in evidence/scripts/plans. Use in-memory PSCredential or SecureString for API requests. Credentials are scoped to authorized origins; they do not make an account disposable. Missing delivery credentials are compatible with queue-only testing.
5. Snapshot state needed for recovery: test-scope and record IDs, exact values and dates, absence versus explicit defaults, counters and relevant worker states. Establish notification isolation before generating messages. Derive the desired final account state from the target application's AGENTS.md/CLAUDE.md and workspace's .agents/skills/peer-review/hints.local.md; it may intentionally differ from the starting state. Keep temporary credentials out of checklist/resume notes.
6. Order the work by dependencies, service, role and configuration state to minimize repeated setup/logins/changes. Run positive controls before rejection/suppression cases. Put final-state verification after all tests. Create `.agents/skills/peer-review/.history/<ticket>/checklist.md` from `templates/checklist.md`; it is the durable coverage and resume ledger, not a second competing plan.

## Present the plan

Preflight must be visible in the chat window, not only tool output or a local file. Begin with a brief statement that preflight is running. After checks and before test execution or fixture/configuration mutations, publish a consolidated **<ticket> | Pre-flight** summary using templates/preflight.md. Show readiness (Ready / Needs input / Blocked), environment, test scope and account role, ticket/source/runtime status, required service readiness and startup/recovery method, account-state readiness and any required feature access or limits, recovery baseline and notification isolation, required/additional/total counts, execution groups, blockers and next action. Mark unknown or unverified items explicitly; do not declare readiness while required inputs remain unresolved. If blocked, publish partial preflight and update it after resolution. Tool output and incremental updates do not replace this summary.

Itemize additional tests with reasons. Do not count setup, cleanup, assertions or repeated controls as added scenarios. Visible preflight is a reporting requirement, not an extra approval gate; continue within existing authorization and the scope rules below.

- With zero to five additional tests, continue automatically within existing authorization.
- With more than five, save the complete ordered checklist and ask how to proceed: all planned tests, required tests only, or a selected additional subset. Include a recommendation. Wait for the answer before executing the test plan; continue only independent read-only preparation while pending. Record the chosen scope and mark omitted tests NOT TESTED with the reason. Do not treat elapsed time as approval.
- If later discoveries expand the proposed additional scope beyond five, apply the same scope question unless the user already authorized that expanded scope. Do not repeatedly ask about an unchanged approved plan.

## Execute and resume

- Follow supported browser/computer-use APIs; use the host browser tools listed under Host agent in SKILL.md. Use focused dialog observations and batch deterministic actions. After Save, verify completion and persistence; AJAX navigation can lag the click. Use browser tests for UI behavior and appropriate APIs/integration for data contracts; do not repeat every assertion at every layer.
- Use `scripts/Invoke-PeerTest.ps1` with a ticket plan in `.agents/skills/peer-review/.history/<ticket>/`. Select compatible authentication/response mode first (README.md). Live runner requests are loopback HTTPS only. Expected records and independently known values must be asserted; success or empty results alone are insufficient.
- Batch all cases per configuration state. Before testing absence of a side effect, prove that side effect with a positive control. Verify the primary operation and relevant stored effects independently. Capture distinct required UI states, important failures and useful final-state proof; keep responses redacted and local.
- Update checklist status and evidence immediately after each completed scenario/batch and before interruptions. Preserve ordered IDs, expected result, actual outcome, configuration, next step and blockers. `[x]` means a terminal result is recorded (PASS, FAIL or deliberately NOT TESTED); BLOCKED stays unchecked with its dependency. Record IN PROGRESS before a mutation and its recovery note. On resume, read this file first, recover unfinished mutations, then continue from the first runnable unchecked item. Do not repeat discovery or completed tests unless revisions, runtime or evidence changed.
- For temporary field/configuration changes, use the guarded fixture helper with the workspace's settings.local.json fixture section via -SettingsPath for both runs and recovery. Derive verified database destinations and table/field allowlists from the application; examples/fixture.example.json is synthetic. Check mappings with -ValidateOnly before mutation. Where the helper does not support the data model, use a narrowly scoped harness with baseline comparison, transaction, finally restoration and independent verification. No browser writes while a DB fixture is active. Revalidate test-scope, record and field mappings against the selected application's data model. A fixture is setup, not proof of UI editing or account provisioning.
- Investigate a failed assertion against relevant code/response/UI and rerun affected cases only. Separate environment failure from implementation failure. Diagnose a dependency once rather than repeating identical requests; apply verified local recovery from the target application's AGENTS.md/CLAUDE.md and workspace's .agents/skills/peer-review/hints.local.md when appropriate. Do not spawn agents by default.
- Append newly discovered bug candidates at the end of checklist.md with stable bug ID, status (candidate/confirmed/disproved), expected/actual behavior, minimal reproduction, source and evidence. Never reorder completed tasks to insert a bug. Record focused investigation/retest actions with the entry. Check intent before confirming; a requirements conflict is not automatically a defect. Update the original entry when resolved rather than accumulating duplicate findings.

## Final state and report

Finish every authorized, runnable required case and resolve stale PARTIAL/BLOCKED items. Retain useful valid test records by default; remove or repair only dirty/invalid data that interferes with future runs. This retention policy does not retain temporary credentials, accidentally queued outgoing messages or weakened security. Remove temporary keys and test messages that could later deliver, restore security/worker/configuration settings, and complete the application's configured final account state, including subscription or limit requirements when applicable. Restore transient counters/overrides when they would contaminate subsequent tests. Preserve normal audit history and record retained fixtures. Verify test messages are clear before restarting delivery.

Use `templates/report.md` to produce `.agents/skills/peer-review/.history/<ticket>/report.md` and a local Jira-ready draft. Report required and additional cases separately; distinguish PASS, FAIL, BLOCKED and NOT TESTED. Include source/runtime provenance, environment, evidence, coverage limitations and final-state verification. Include a **Bugs Found** section with confirmed findings and evidence, or **None found**; put unresolved observations/conflicts separately. Never hide unresolved failures behind an overall PASS. Posting needs authorization.

Format the final chat summary using templates/summary.md: ticket/title, bold overall result and **Total run time** at the top, a compact coverage table separating required and additional cases with PASS/FAIL/BLOCKED/NOT TESTED counts, then concise findings with stable IDs and pre-existing attribution where verified. Follow with material coverage limitations and meaningful report/evidence links. Omit final-state/restoration details from the final chat summary; keep verification in the checklist and detailed report. If an incomplete restoration requires user action, identify it as a blocker. Count failed cases separately from unique bugs. Make PASS and FAIL visually distinct in all displayed test grids: use **✅ PASS** and **❌ FAIL** for individual outcomes, and **✅ PASS** / **❌ FAIL** in coverage column headers. Retain the words so meaning does not depend on color or icons. Keep machine-readable statuses and checklist status values unchanged. State whether the Jira draft was posted. Use short headings, aligned Markdown tables and plain language; avoid dense paragraphs, raw logs and oversized screenshots in the opening summary. Put any required proof screenshot after summary/links. Keep the full matrix and technical provenance in the report. Do not omit untested cases or timing gaps for presentation.

Runner results cover API assertions only; merge their evidence into the ticket checklist/report without overwriting the full ticket report. Save runner output in a per-batch subdirectory. Track actual request counts separately from total run time and runner time; use actual token usage only if available. Do not invent savings. Give concise progress updates at least once per minute.

## Runner usage

```powershell
$runnerPath = Join-Path $skillDirectory 'scripts/Invoke-PeerTest.ps1'
& $runnerPath -PlanPath $ticketPlan -OutputDirectory $batchEvidence -Credential $testCredential
# Offline response validation:
& $runnerPath -PlanPath $ticketPlan -OutputDirectory $batchEvidence -ReplayDirectory $savedResponses
```

Plans use relative API endpoints and assertions: Equals, IsNull, Present, EqualField, AbsentPattern, Matches, Count, MinCount. Synthetic format: `plans/example-search.json`. Empty filtered record sets fail. Legacy defaults are credential POST, HTTP 200 and ResultCode=0; key GETs, raw responses and expected errors are explicit (README.md). Replay makes no network calls and proves no current website behavior.
